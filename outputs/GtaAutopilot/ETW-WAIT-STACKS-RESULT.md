# Уточнение ожиданий ORT и проверки GPU-провайдера

4 ноября 2026. Анализ уже сохранённого ETL, без новой записи/захвата/игрового ввода. **В сохранившихся пользовательских стеках ожидание внутри ONNX Runtime проходит через системный WaitForSingleObject.** Это уже конкретное место блокировки, но тип ожидаемого объекта и его связь с GPU-fence ещё не установлены.

## Стеки

Исследован workerTID4928/PID6384 из etw-bounded-20261104-125421-823. Извлечено1443StackWalk-события этого потока.986из них сопоставлены с CSwitch по точному QPC; это switch-in, не switch-out. Поэтому состояние старого потока из того же события не приписывалось нашему worker. Для сопоставления взято предыдущее переключение **с** worker и проверено его OldThreadState=Waiting.28событий стека связаны с такими возобновлениями; kernel/user-части могут идти отдельными событиями, это не28независимых вызовов.

В7одинаковых пользовательских стеках:

```text
ntdll.dll+0x161dd4
KernelBase.dll+0x1be9f
onnxruntime.dll+0xdad7a
onnxruntime.dll+0x15ec61
... onnxruntime.dll ...
onnxruntime_binding.node
node.exe
```

Адреса модулей взяты из Image rundown данного PID, не из адресов других процессов. В локальных системныхDLL экспорт NtWaitForSingleObject имеетRVA0x161dc0, то есть верхний адрес стека соответствует +0x14. WaitForSingleObjectEx имеетRVA0x1bdf0, следующий адрес соответствует +0xaf. Проверка выполнена через GetModuleHandle/GetProcAddress над уже загруженными системнымиDLL, без вызова функций ожидания. Имена внутренних функций ORT поPDB не разрешены; совпадение экспортов текущих системныхDLL применимо при неизменной их версии, отдельного полногоPDB-сопоставления не было.

Примеры возобновлений этой цепочки: предшествующий off-CPU интервал74,029мс и129,740мс, OldThreadWaitReason=6(UserRequest). Это хорошо согласуется с ранее посчитанными окнамиYOLOP121 иSegFormer122. Off-CPU включает Waiting **и** Ready, его нельзя заново прибавлять к прежним CPU-state таблицам.

Стек в момент возобновления показывает путь возврата из ожидания, а не сам стек входа в блокировку. Не восстановлены handle/тип ожидаемого объекта. Поэтому нельзя объявлять причиной allocator mutex, V8 GC, CPU-shape-boundary либо DML fence. Но длинная пауза в этих примерах действительно связана с системным ожиданием из нативного ORT-пути, а не только с готовым к исполнению, но вытесненным JavaScript.

## Почему GPU-таймлайн отсутствует

GUID DxgKrnl проверен по [Microsoft/Intel PresentMon](https://github.com/GameTechDev/PresentMon/blob/main/PresentData/ETW/Microsoft_Windows_DxgKrnl.h):802ec45a-1e99-4b83-9920-87c98277ba9d, в нашем профиле опечатки нет.

Проверена не только XML-расшифровка. В41МБboundedETL последовательность байтов ProviderGUID в формате Windows GUID отсутствует полностью. Это делает объяснение одним неудобным отображением tracerpt недостаточным: нужный провайдер в этом файле не обнаруживается даже на уровне бинарных заголовков. Отсутствие данных не означает отсутствие GPU-работы.

В старом15,7ГБ ETL etw-20261104-123552-589 (записывался штатным GeneralProfile+GPU) GUID найден на смещении86 946 952. Предшествующие24байта имеют согласованный EVENT_HEADER:Size256,TID14656,PID14308,QPC4524261196,EventId514. Это проверка наличия хотя бы одного события нужного провайдера, не полная расшифровка очередей/копирования и не восстановление прогона Node. Старый ETL относится к иной попытке/времени и не объединяется с новым как одна запись.

Следовательно, искать проблему нужно в настройке/активации GPU-сбора нового custom-профиля, а не начинать с замены модели или объяснения отсутствия событий декодером. Из наблюдения пока не выделено одно причинное отличие: штатныйGPU-профиль содержит дополнительные providers, NonPagedMemory/Stack и CaptureStateOnStart, которых нет в минимальном. Приём WPR XML подтверждает синтаксис, но не фактическое поступление GPU-событий. Для исправления нужен короткий GPU-only preflight и проверка появления реальных событий до следующего большого модельного опыта.

## Практическое решение

Повторять текущий bounded-профиль без проверки не следует. Следующая запись должна заранее пройти проверку активности GPU-провайдера и сохранения достаточного CPU-интервала; для CPU нужно снизить глобальную детализацию/объём стеков либо увеличить кольцо/сократить окно. Определять длительность shader/copy/queue по одному WaitForSingleObject нельзя. Данные пока не доказывают полезность переписывания OCR/смены языка или полного удаленияSegFormer.

Файлы анализа: work/etw/bounded-analysis/wait-stacks.py,wait-stacks.json,system-exports.json. Сохранены исходные адреса и неразрешённые кадры, никакие имена ORT-функций не придуманы. Исходные ETL/Node JSON и производственный код/модели не менялись. WPR по-прежнему остановлен, новых записей не запускалось. Производственные тесты не повторялись; проверялись точные QPC/TID-сопоставления, диапазоны модулей и экспортныеRVA.
